## Run in two minutes

Python 3.10+; no mandatory packages. Run from the repository root:

```sh
python -m agent.pipeline --workers 6
python -m agent.review --apply
python -m agent.pipeline --analyze-only
python -m agent.build
python -m unittest discover -s tests -v
python -m http.server 8000 --directory site
```

Open http://localhost:8000. `--limit 5` is useful for a small collection run, but existing cached/output rows are retained. Use a fresh checkout for a truly isolated small run. `--refresh` bypasses the retrieval cache. A failed document is recorded, while a failed app/model call makes the run exit nonzero. Outputs are checkpointed after each app so interrupted runs retain progress.

The checked-in results are a real **public-document retrieval + AI-session-assisted evidence-rule run**. Codex inspected source excerpts, identified semantic traps, authored exceptions and caveats, and helped implement the pipeline. No unattended LLM API or Composio SDK call was used in that recorded run. Do not describe the checked-in data as an autonomous model-powered crawl.

## Optional autonomous model mode

Set `OPENAI_API_KEY` in your shell, then:

```sh
python -m agent.pipeline --mode ai --workers 3
python -m agent.build
```

`OPENAI_MODEL` defaults to `gpt-4.1-mini`. This mode uses the OpenAI Chat Completions API with JSON output. Each app gets an extraction call and a second model critique, followed by schema and quote checks. The API-key mode is implemented but was **not live-tested** because no key was supplied. Model usage is recorded per row. Costs depend on the selected model and document sizes; the pipeline does not purchase credits or create customer accounts.

Do not run `agent.review --apply` after model mode unless you intentionally want to replace model findings with the deterministic evidence rules. These are alternative extraction paths sharing collection and analysis.

## Is Composio SDK or MCP necessary?

No. The brief explicitly permits an agent, script or pipeline and encourages Composio in the spirit of the role. Its search tools are useful for discovery, but an SDK is not needed to investigate documentation or wrap a REST API as an MCP tool.

An optional Composio SDK discovery adapter is included:

```sh
python -m pip install -r requirements-composio.txt
# Set COMPOSIO_API_KEY and optionally COMPOSIO_USER_ID in your shell.
python -m agent.pipeline --composio --workers 3
```

It invokes `COMPOSIO_SEARCH_DUCK_DUCK_GO` with pinned toolkit version `20260903_00`, and saves raw discovery responses under ignored `data/raw/`. Discovered URLs are **not silently promoted into evidence**: review official-domain matches and add relevant URLs to `data/apps.json`, then rerun collection. This adapter is untested with a live credential. There is no claim that Composio verified these findings. No keys are required to read the report.

Official references: [Composio search toolkit](https://docs.composio.dev/toolkits/composio_search), [direct execution and version pinning](https://docs.composio.dev/docs/tools-direct/executing-tools).

## Architecture Uday can explain

1. **Seeds:** `data/apps.json` preserves the supplied identities and categories, and targets public official docs. The uploaded reference contained only 90 apps; Uday supplied the exact final 10. This is a provided customer-request set, not a random sample of the software market.
2. **Collection:** `agent/pipeline.py` fetches public docs concurrently with request timeouts, retries, bounded response reads and caching. It decodes compressed responses and prefers main content. Failures, redirects, timestamps and text hashes are retained. It cannot fully render JavaScript sites.
3. **First pass:** simple keywords produce intentionally untrusted candidates. The snapshot is `data/first-pass.json`; it is a keyword baseline, not a fabricated “low-accuracy LLM” run.
4. **Refinement:** `agent/review.py` replays the AI-assisted source-specific exceptions and conservative rules. Every matched claim retains exact supporting excerpts. It strips generic pricing/footer mentions, rejects API credentials belonging to external services, and keeps unknown MCP when only a nav label is found.
5. **Verification:** citation IDs must exist and quoted text must appear in readable evidence. That proves quote grounding only, not semantic truth. `data/review-log.json` records before/after changes. `data/challenge-checks.json` records an AI-adjudicated diagnostic set; `data/human-review.json` is separate.
6. **Analysis and report:** aggregate counts are calculated from results, not handwritten. The static page has no backend, database or client-side secrets. JSON and CSV make the result agent-readable; app details and sources make it human-readable.

Descriptions and caveats are AI summaries/inferences, labelled accordingly. API breadth is limited to the retrieved documentation slice rather than an invented endpoint census. Toolkit verdicts are scoped feasibility recommendations: **buildable** for a few documented low-friction/local prototypes; **conditional** when a callable surface exists but onboarding/permissions need proof; **unknown** when evidence is insufficient. None means production integration was tested.

## Verification and honest before/after

The AI diagnostic set deliberately contains nine ambiguity/error cases and three controls. It compares recorded first/final auth values with source-adjudicated expected values. It is **not random, independent, human-reviewed or an accuracy estimate over 100 apps**.

Examples include Clay (outbound third-party API credentials misread as Clay auth), Harvest (legacy Basic auth reported as current), MongoDB Atlas (Digest vs Basic and recommended service-account OAuth), Otter (a mention of unavailable API keys misread as support), and BigCommerce (external tax-provider Basic auth misread as core store auth).

For the broader human worksheet, two apps per category are selected using seed 42. Check auth, access and feasibility against live official docs. It begins blank. Enter reviewer identity, date, source URL, expected value, notes and whether the first/final answer was correct. Only complete, attributed human records with actual booleans count; duplicate app/field checks count once. Uncertain or inaccessible checks remain unscored. A small targeted human check can supplement the stratified sample, but should be labelled with its selection method.

Regenerate the analysis and report after real human checks:

```sh
python -m agent.pipeline --analyze-only
python -m agent.build
```

Do not convert AI reviews into human records or invent sample accuracy. The page reports “Pending” until scored human checks exist. Even a completed sample measures field accuracy on that sample, not an unbiased population estimate.

## Limits and next steps

Access eligibility is still unknown for many apps. Category access charts are an evidence-coverage view, not a market-wide claim about which categories are easiest. API auth pages may omit other supported methods. MCP “unknown” means unconfirmed in this set. Consumer NotebookLM and its Enterprise API are distinct. Ramp's developer-docs MCP reads documentation and is not proof of a transaction toolkit. Paygent Connect remains identity-ambiguous; iPayX's supplied docs route does not expose usable API docs. JavaScript shells and stale links require browser retrieval or outreach.

No production API actions, payment tests or customer credential issuance were performed. To deepen the submission: finish the human sample; retrieve access/plan-specific sources for unresolved apps; prove one read-only prototype with actual credentials; rerun uncertain records; and measure accuracy on a fresh sample after refining prompts/rules.
